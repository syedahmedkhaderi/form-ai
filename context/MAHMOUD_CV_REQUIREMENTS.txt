4. EXTRACTION SCRIPT (reference behavior)

This is the contract behavior, not final code. Keep it this simple.

  import cv2, numpy as np, mediapipe as mp
  from mediapipe.tasks import python as mp_python
  from mediapipe.tasks.python import vision

  def extract_clip(video_path, task_path="pose_landmarker_full.task"):
      base = mp_python.BaseOptions(model_asset_path=task_path)
      opts = vision.PoseLandmarkerOptions(base_options=base,
                                          running_mode=vision.RunningMode.VIDEO,
                                          num_poses=1)
      landmarker = vision.PoseLandmarker.create_from_options(opts)
      cap = cv2.VideoCapture(video_path)
      fps = cap.get(cv2.CAP_PROP_FPS) or 30.0
      frames = []
      idx = 0
      while True:
          ok, frame = cap.read()
          if not ok:
              break
          rgb = cv2.cvtColor(frame, cv2.COLOR_BGR2RGB)
          mp_img = mp.Image(image_format=mp.ImageFormat.SRGB, data=rgb)
          ts_ms = int(idx * 1000.0 / fps)
          res = landmarker.detect_for_video(mp_img, ts_ms)
          if res.pose_landmarks:
              lms = res.pose_landmarks[0]
              row = np.array([[p.x, p.y, p.z, p.visibility] for p in lms], dtype=np.float32)
          else:
              row = np.full((33, 4), np.nan, dtype=np.float32)   # no detection this frame
          frames.append(row)
          idx += 1
      cap.release()
      return np.stack(frames, axis=0), fps   # [T,33,4], fps

Rules:
  - Always 33 rows per frame, even when detection fails (fill NaN). Syed drops NaN frames in preprocessing.
  - Save with np.save(path, arr). float32. Never change axis meaning: [frame, landmark, (x,y,z,visibility)].
  - One video clip = one rep = one tensor = one manifest row.


5. DATA COLLECTION PLAN (this is where the project is won or lost)

The model is only as good as your clips. Aim for breadth over polish.

  Target counts (minimum viable, per exercise):
    good form    : 60 to 100 clips
    each bad type: 30 to 50 clips
  Squat bad types: knee_valgus, insufficient_depth, back_rounding
  Curl bad types : swing, partial_rom, elbow_flare

  Variety that matters (vary deliberately, label honestly):
    - at least 6 to 8 different people (subject_id), so the split in section 7 can hold people out
    - both sexes, range of body sizes and heights
    - different clothing, lighting, backgrounds
    - the camera setup from contracts section 4 (front 3/4 for squat, front for curl)

  Labeling: you record a clip and you KNOW what it is because you direct it. Tell the person "do 5 squats with your knees caving in" and label those knee_valgus. Intentional bad form is the fastest way to get balanced classes. This is legitimate and standard for form-correction datasets.

  Fill manifest.csv as you go, never in a batch at the end. Both label and error_type for every clip.


6. HOW YOUR OUTPUT CONNECTS

  To Syed: he loads your .npy files and manifest.csv, applies the preprocessing in contracts section 7, and trains. He needs your tensors to be RAW (no normalization) and shaped exactly [T,33,4]. That is the entire interface. If your shapes are right, his loader just works.

  To Islam: indirectly. Islam runs the same MediaPipe landmarker on the phone, so the live 33 landmarks match your offline ones. You owe him nothing but a confirmation that he pinned MediaPipeTasksVision and is using the same 33-landmark output.


7. TRAIN/VAL SPLIT HYGIENE (tell Syed, but it starts with you)

Because you record multiple clips per person, the same person must never appear in both train and validation. That is why subject_id exists. If you skip it, the model looks great in testing and collapses in the demo on a new body. Keep subject_id accurate per clip.
