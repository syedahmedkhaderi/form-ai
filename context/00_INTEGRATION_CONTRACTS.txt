FORMAI - INTEGRATION CONTRACTS (READ FIRST)
Shared specification for Mahmoud (CV), Syed (Model), Islam (App).
Lock this on Day 0. Nothing below should change once the three of you agree, because every interface depends on it.

Exercises in scope: bodyweight squat, single-arm dumbbell curl. Nothing else.


1. WHY THIS DOCUMENT EXISTS

The three parts run in parallel and only meet at the end. They connect at exactly three seams:
  Mahmoud -> Syed   : keypoint tensors + labels (offline training data)
  Syed -> Islam     : a Core ML model + the exact preprocessing recipe
  Mahmoud -> Islam  : agreement that both extract the SAME 33 landmarks

If the keypoint schema, feature order, or model input/output names differ by even one element between offline and on-device, the model fails silently on the phone. This file removes that risk by fixing all of it up front.


2. THE ONE DECISION THAT MAKES THIS WORK

Pose detector is MediaPipe Pose Landmarker on BOTH sides:
  - Offline (Mahmoud): mediapipe Python -> 33 landmarks per frame.
  - On-device (Islam): MediaPipeTasksVision (iOS CocoaPod) -> the same 33 landmarks.

Do NOT use Apple Vision body pose on-device. Its landmark count and ordering differ from MediaPipe, which would silently break a model trained on MediaPipe keypoints. Same detector, same schema, no surprises. You already used this exact landmarker in Rehabify.


3. KEYPOINT SCHEMA (canonical)

MediaPipe Pose, 33 landmarks, indices 0..32. Per landmark store 4 floats: x, y, z, visibility.
  x, y : normalized to [0,1] relative to image width/height.
  z    : depth (we DROP z in features, it is noisy; keep it in raw tensors anyway).
  visibility : [0,1].

Landmarks used by FormAI (memorize these indices):
  11 left_shoulder    12 right_shoulder
  13 left_elbow       14 right_elbow
  15 left_wrist       16 right_wrist
  23 left_hip         24 right_hip
  25 left_knee        26 right_knee
  27 left_ankle       28 right_ankle


4. CAMERA SETUP (must match between training videos and live app)

Phone on the floor or a stand, roughly 2.5 to 3 meters away, portrait, whole body in frame.
  - Squat: front 3/4 view (camera slightly to the side so both depth and knee tracking are visible).
  - Curl: front view of the working side.
Mahmoud records training clips in this setup. Islam shows the same framing guide in-app. If the views diverge, the model sees a distribution it never trained on.


5. SEAM A - TENSOR FORMAT (Mahmoud -> Syed)

Unit of data = ONE rep = ONE clip = ONE label. Keep clips short (a single rep, good or bad).

Per clip, two artifacts:
  a) Raw landmark array, saved as float32 .npy, shape [T, 33, 4]
       T = number of frames in the clip
       axis 1 = landmark index 0..32
       axis 2 = [x, y, z, visibility]
     No normalization here. Mahmoud delivers RAW landmarks. All preprocessing is Syed's job (section 7), so there is exactly one source of truth for it.
  b) One row in manifest.csv (see below).

Directory layout:
  formai_data/
    squat/clip_0001.npy, clip_0002.npy, ...
    curl/clip_0001.npy, ...
    manifest.csv

manifest.csv columns (exact header, in order):
  clip_id,file,exercise,view,label,error_type,subject_id,fps,num_frames,notes

  clip_id    : unique string, e.g. squat_0001
  file       : path relative to formai_data, e.g. squat/clip_0001.npy
  exercise   : squat | curl
  view       : front | threequarter | side
  label      : good | bad
  error_type : squat -> none | knee_valgus | insufficient_depth | back_rounding
               curl  -> none | swing | partial_rom | elbow_flare
  subject_id : anonymized person id (so train/val split never leaks a person across both)
  fps        : capture frames per second (e.g. 30)
  num_frames : T
  notes      : free text, optional

label is the binary target for v1. error_type is the multi-class target for v2 if data volume allows. Mahmoud fills BOTH columns for every clip so Syed can choose later without re-labeling.


6. SEAM B - MODEL ARTIFACT (Syed -> Islam)

Two Core ML models, one per exercise:
  SquatFormScorer.mlpackage
  CurlFormScorer.mlpackage

Format: mlprogram, minimum deployment target iOS17.

Input  : name "keypoint_window", float32, shape (1, W, F)
Output : name "form_logits", float32, shape (1, NUM_CLASSES)

W and F are fixed per exercise (defaults in section 7). Islam applies softmax + argmax on form_logits and maps the index to a label using the published class list.

Each model ships with a sidecar model_card.json:
  {
    "exercise": "squat",
    "W": 32,
    "F": 21,
    "feature_order": [ ... exact ordered feature names ... ],
    "class_labels": ["good", "knee_valgus", "insufficient_depth", "back_rounding"],
    "normalization": "hip-center origin, torso-length scale (see contracts sec 7)",
    "version": "v1",
    "built": "2026-06-16"
  }

The feature_order list is the contract Islam re-implements in Swift. If Syed changes it, the model_card changes and Islam updates. Nothing else couples them.


7. SEAM A+B GLUE - PREPROCESSING RECIPE (owned by Syed, mirrored by Islam)

This is the most important section. The function "raw landmarks -> model input tensor" must be byte-for-byte identical offline and on-device. It is written once here as plain math. Syed implements it in Python, Islam ports the same steps to Swift.

Inputs to the recipe: one rep's frames, each a row of 33 landmarks (x,y) plus visibility. z is ignored.

Step 1. Per-frame normalization (translation + scale invariant)
  hip_mid    = (L_hip[23] + R_hip[24]) / 2          # using (x,y)
  sh_mid     = (L_shoulder[11] + R_shoulder[12]) / 2
  scale      = euclidean_distance(sh_mid, hip_mid)  # torso length
  if scale < 1e-4: drop this frame (person not detected well)
  For every used landmark p:  p_norm = (p - hip_mid) / scale
  Result: hip is the origin, body is unit-torso scaled. Distance from camera no longer matters.

Step 2. Build the per-frame feature vector (exercise-specific, ORDER IS THE CONTRACT)

  Angle helper: angle_at_B(A,B,C) = degrees of the angle ABC, then divide by 180 to map to [0,1].

  SQUAT, F = 21, feature_order:
    [ 11x,11y, 12x,12y, 23x,23y, 24x,24y, 25x,25y, 26x,26y, 27x,27y, 28x,28y,   # 16 normalized coords
      left_knee_angle,        # angle_at_B(23,25,27)/180
      right_knee_angle,       # angle_at_B(24,26,28)/180
      torso_lean,             # angle between (sh_mid - hip_mid) and vertical axis, /180
      left_valgus,            # (25x_norm - 27x_norm)   knee_x minus ankle_x in normalized space
      right_valgus ]          # (26x_norm - 28x_norm)
    All coords above are the normalized values from Step 1.

  CURL, F = 11, feature_order (model assumes RIGHT arm working):
    [ 12x,12y, 14x,14y, 16x,16y, 11x,11y,   # 8 normalized coords (R shoulder, R elbow, R wrist, L shoulder)
      right_elbow_angle,      # angle_at_B(12,14,16)/180
      shoulder_tilt,          # angle between (R_shoulder - L_shoulder) and horizontal, /180  (detects body sway)
      elbow_flare ]           # (14x_norm - 12x_norm)  elbow_x minus shoulder_x in normalized space
    If the user selects LEFT arm in-app, mirror every x as x_mirror = -x BEFORE Step 1 ordering (i.e. negate normalized x of all landmarks), then read left-arm indices into the same slots. Easiest: Islam flips horizontally so a left-arm rep looks like a right-arm rep to the model. One model, both arms.

Step 3. Resample the rep to fixed length W = 32
  A rep has variable T frames. Linearly interpolate each of the F feature channels along time from T points to exactly W=32 points.
  Result: a fixed [W=32, F] matrix. Add batch dim -> [1, 32, F]. This is "keypoint_window".

That is the entire model input. Same three steps, same constants (W=32, the F feature lists, the 1e-4 floor), on both sides.


8. SEAM C - REP COUNTING (rule-based, on-device, NOT the ML model)

Rep detection is deterministic and lives in the app. It does two jobs: count reps, and segment frames into per-rep windows that feed the model.

  Squat: track left_knee_angle (or hip vertical position).
    state DOWN when knee_angle < 100 deg, state UP when knee_angle > 160 deg.
    Count one rep on the DOWN->UP transition. The frames from one UP, through DOWN, back to UP = one rep clip.
  Curl: track right_elbow_angle.
    state FLEXED when elbow_angle < 60 deg, EXTENDED when elbow_angle > 150 deg.
    Count one rep on FLEXED->EXTENDED transition.

Thresholds are starting points; tune on real clips. Because the rep counter already computes the same joint angles the model uses, it is also the graceful fallback: if the ML model underperforms on limited data, Islam can ship threshold-based cues from these angles for the demo (this is the Rehabify approach). System degrades gracefully, demo never dies.

10. QUICK REFERENCE (pin these numbers)

  Pose detector     : MediaPipe Pose Landmarker, 33 landmarks, [x,y,z,visibility]
  Raw tensor        : float32 .npy, shape [T,33,4], one clip = one rep = one label
  Window W          : 32 frames (resampled per rep)
  Squat features F  : 21  (see sec 7 order)
  Curl features F   : 11  (see sec 7 order, right-arm canonical)
  Model format      : Core ML mlprogram, iOS17
  Model input       : keypoint_window, float32, (1, W, F)
  Model output      : form_logits, float32, (1, NUM_CLASSES)
  Export pins       : torch 2.4.0, coremltools 8.1, numpy 1.26.4 (verified working together)
